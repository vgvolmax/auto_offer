# Разметка прайсов в `catalog_bundle`

Выполни эту инструкцию в новом чате, используя приложенные
`catalog-validation-kit.mjs` и один или несколько исходных прайсов.
`catalog-validation-kit.mjs` является единственным источником taxonomy,
классов, JSON Schemas, semantic rules и допустимых canonical values. Не
используй знания о контрактах вне этого файла и не изменяй его содержимое.

Внутри `catalog-validation-kit.mjs` доступны читаемые экспорты:

- `annotationKit` — taxonomy, `class_schema_ids`, `schemas_by_id` и
  `root_schema_id`;
- `classSchemaRegistry` — разрешённые annotation paths, critical fields,
  evidence policy и class-specific semantic contract;
- `kitMetadata` — версии и SHA-256 исходных контрактов;
- `validateCatalogBundle` — полный структурный и семантический валидатор.

## Результат

Для **каждого** исходного прайса создай отдельный скачиваемый UTF-8 JSON-файл
`catalog.<catalog_id>.json` с `kind: "catalog_bundle"`. Корневая схема:
`https://example.local/schemas/bundles/catalog-bundle.schema.json`.
Используй только `annotationKit.schemas_by_id`, включая embedded
`schemas_by_id`, и class schema из `annotationKit.class_schema_ids`.

Самостоятельно прочитай исходные файлы, включая Excel с несколькими листами.
Пользователь не должен конвертировать, подготавливать или разбивать их. Можно
обрабатывать большой файл внутренними частями, но результат для одного прайса
должен быть единым и завершённым. Нельзя выдавать частичный файл как готовый.

## Извлечение строк

1. Определи листы, заголовки таблиц, товарные строки и контекст разделов.
2. Не считай товарами заголовки, подзаголовки, пустые строки, итоги,
   примечания и служебные строки. Не пропускай ни одной реальной товарной
   строки; о любом неизвлечённом фрагменте сообщи явно.
3. Для каждой товарной строки сохрани точные исходные значения отдельно в
   `source`. В `source.raw_fields` перенеси все заполненные исходные колонки.
   Не нормализуй исходные SKU, GTIN, цены, единицы или названия.
4. Если стандартной колонки нет, необязательное поле можно не добавлять. Если
   колонка есть, но ячейка пуста, используй `null`, только когда schema это
   допускает.
5. В `source.source_position.sheet` укажи точное имя листа, а в
   `source.source_position.row` — исходный номер строки. Создай стабильный
   `source_item_id` из имени листа и номера строки.
6. Создай допустимый schema `catalog_id` на основе имени файла. Добавляй
   `source_sha256` лишь если можешь вычислить точный SHA-256 исходных байтов;
   иначе не добавляй поле. `item_count` должен точно равняться длине `items`.

## Смысловая разметка

Для каждой товарной строки выбери один из классов
`annotationKit.taxonomy.classes` и примени соответствующую catalog class schema.
Исходные данные должны находиться только в `source`, а созданная смысловая
разметка — только в `catalog_item`. Контекст раздела можно использовать для
классификации только с соответствующим evidence.

Извлекай лишь подтверждённые документом сведения и не выдумывай отсутствующие
характеристики. Для каждого значения, полученного смысловой интерпретацией,
добавь evidence. Все ссылки на поля в annotation/evidence должны быть RFC 6901
JSON pointers.

Используй `unknown_fields`, `ambiguities`, `issues` и статус `needs_review`
строго по `classSchemaRegistry`. Не добавляй pointer в `unknown_fields`, если
по нему уже сохранено подтверждённое ненулевое значение. Не добавляй ambiguity
на подтверждённое значение без связанного `issues[].json_pointer`. Каждый
отсутствующий critical field должен быть явно объяснён через `unknown_fields`,
`ambiguities` либо `issues` с тем же pointer.

`validated` допустим только при выполнении class schema и semantic contract.
При нехватке обязательного признака ставь `needs_review` и корректно объясняй
отсутствующее поле. При неоднозначном классе выбери наиболее подтверждённый,
зафиксируй ambiguity по правилам registry и снизь confidence.

Статусы `validated`, `needs_review` и `invalid` относятся к отдельной товарной
разметке. Они не разрешают выдавать bundle, нарушающий контракт. Bundle с любой
ошибкой полного валидатора не считается готовым.

Если строку нельзя отнести к классу без выдумывания, не скрывай её и не
объявляй bundle полностью готовым. Если файл нельзя надёжно прочитать либо
нельзя построить полный валидный bundle, остановись и назови конкретную
причину, не создавая правдоподобный неполный результат.

## Жёсткие запреты

- Не выполняй matching или подбор товаров, не вычисляй similarity score и не
  создавай `product_id`, `offer_id` или `match_level`.
- Не исправляй, не проверяй, не угадывай и не нормализуй GTIN или артикулы.
  Никогда не переноси SKU или GTIN в AI-generated identity.
- Не обращайся к внешним catalog data и не добавляй неподтверждённые значения.
- Не ослабляй, не переписывай и не обходи `validateCatalogBundle`.

## Обязательная полная проверка

Одной проверки JSON Schema недостаточно. Перед выдачей программно проверь
каждый результат полным валидатором из `catalog-validation-kit.mjs`.

При доступе к Node запусти:

```bash
node catalog-validation-kit.mjs <file>
```

Либо импортируй `validateCatalogBundle` из MJS и передай ему разобранный JSON.
Результат готов только при `valid: true` и пустом массиве `errors`.

Если валидатор вернул ошибку, используй её `code`, `path` и `message`, исправь
только соответствующую проблему и повтори проверку. Продолжай цикл до
`valid: true`. Не утверждай, что файл валиден, если полный валидатор не был
запущен. Файл с ошибками не считается готовым и не должен выдаваться как
финальный.

## Выдача

Не печатай полный JSON в сообщении: приложи только скачиваемый UTF-8 JSON-файл.
После каждого файла дай краткую сводку:

- общее количество строк;
- количества `validated`, `needs_review`, `invalid`;
- подтверждение, что полный `validateCatalogBundle` вернул `valid: true`.
