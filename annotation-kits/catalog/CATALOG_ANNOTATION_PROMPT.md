# Разметка прайсов в `catalog_bundle`

Выполни эту инструкцию в новом чате, используя приложенные
`catalog-annotation-kit.json` и один или несколько исходных прайсов. Комплект
является единственным источником taxonomy, 41 класса, JSON Schemas и допустимых
canonical values. Не используй знания о контрактах вне комплекта и не изменяй
и не пересказывай его содержимое.

## Результат

Для **каждого** исходного прайса создай отдельный скачиваемый UTF-8 JSON-файл
`catalog.<catalog_id>.json` с `kind: "catalog_bundle"`. Проверяй его по
`root_schema_id` комплекта:
`https://example.local/schemas/bundles/catalog-bundle.schema.json`, разрешая
все ссылки только через embedded `schemas_by_id`.

Самостоятельно прочитай исходные файлы, включая Excel с несколькими листами.
Пользователь не должен конвертировать, подготавливать или разбивать их. Можно
обрабатывать большой файл внутренними частями, но результат для одного прайса
должен быть единым и завершённым. Нельзя выдавать частичный файл как готовый.

## Извлечение строк

1. Определи листы, заголовки таблиц, товарные строки и контекст разделов.
2. Не считай товарами заголовки, подзаголовки, пустые строки, итоги,
   примечания и служебные строки. Не пропускай ни одной реальной товарной
   строки; о любом неизвлечённом фрагменте сообщи явно.
3. Для каждой товарной строки сохрани точные исходные значения отдельно в
   `source`. В `source.raw_fields` перенеси все заполненные исходные колонки.
   Не нормализуй исходные SKU, GTIN, цены, единицы или названия.
4. Если стандартной колонки нет, необязательное поле можно не добавлять. Если
   колонка есть, но ячейка пуста, используй `null`, только когда schema это
   допускает.
5. В `source.source_position.sheet` укажи точное имя листа, а в
   `source.source_position.row` — исходный номер строки. Создай стабильный
   `source_item_id` из имени листа и номера строки.
6. Создай допустимый schema `catalog_id` на основе имени файла. Добавляй
   `source_sha256` лишь если можешь вычислить точный SHA-256 исходных байтов;
   иначе не добавляй поле. `item_count` должен точно равняться длине `items`.

## Смысловая разметка

Для каждой товарной строки выбери один из 41 классов и примени catalog class
schema, указанную для класса в kit. Исходные данные должны находиться только в
`source`, а созданная смысловая разметка — только в `catalog_item`. Контекст
раздела можно использовать для классификации только с соответствующим
evidence.

Извлекай лишь подтверждённые документом сведения и не выдумывай отсутствующие
характеристики. Для каждого значения, полученного смысловой интерпретацией,
добавь evidence. Все ссылки на поля в annotation/evidence должны быть RFC 6901
JSON pointers. Используй `unknown_fields`, `ambiguities` и статус
`needs_review`: `validated` допустим только при выполнении всех требований
class schema. При нехватке обязательного признака ставь `needs_review`. При
неоднозначном классе выбери наиболее подтверждённый, зафиксируй ambiguity и
снизь confidence.

Если товарную строку нельзя честно отнести к taxonomy class, не удаляй её:
полностью сохрани `source`, сформируй `source_item_id` и создай отдельный
`catalog_item` со `schema_version`, `taxonomy_version` и `annotation.status` =
`unsupported`. Не добавляй приблизительный или fallback `class_id`, а также
`identity`, `attributes` или `ports`. Обязательно укажи `annotation.reason_code`:
`NO_TAXONOMY_CLASS`, когда ни один класс не подходит; `AMBIGUOUS_CLASS`, когда
два или более класса действительно равновероятны; `UNCLASSIFIABLE_SOURCE`,
когда источник не позволяет классифицировать товар. `needs_review` используй
только тогда, когда `class_id` уже установлен достаточно надёжно. Если сам файл
нельзя надёжно прочитать, остановись и назови конкретную причину, не создавая
правдоподобный неполный результат.

## Жёсткие запреты

- Не выполняй matching или подбор товаров, не вычисляй similarity score и не
  создавай `product_id`, `offer_id` или `match_level`.
- Не исправляй, не проверяй, не угадывай и не нормализуй GTIN или артикулы.
  Никогда не переноси SKU или GTIN в AI-generated identity.
- Не обращайся к внешним catalog data и не добавляй неподтверждённые значения.

## Выдача и проверка

Перед выдачей программно проверь каждый результат по `root_schema_id` и
embedded `schemas_by_id`. Не утверждай, что файл валиден, если программная
проверка не выполнена. Не печатай полный JSON в сообщении: приложи только
скачиваемый файл. После каждого файла дай только краткую сводку: общее
количество строк и количества `validated`, `needs_review`, `invalid`, `unsupported`.

## Explicit fact preservation audit

**EXPLICIT SOURCE FACT MUST NOT DISAPPEAR.** Перед финальной выдачей каждой позиции проведи semantic fact audit: каждый materially relevant технический факт, явно присутствующий в `source.raw_name` или `source.raw_fields`, должен либо попасть в соответствующее поле `identity` / `attributes` / `ports`, либо быть отражён в `unknown_fields`, `ambiguities` или `issues`, если честная нормализация неоднозначна. Запрещён результат «source содержит факт → output его теряет → `annotation.status = validated`». Это правило дополняет, а не отменяет запрет выдумывать отсутствующие факты.

Обязательные pattern-проверки:

- `20x1/2\"`, наружная резьба: сохрани обе стороны — PPR 20 mm и male thread 1/2\". Если connection semantics неоднозначна, поставь `needs_review`, но не удаляй размер.
- переходной tee `25x20x25`: сохрани три соответствующих размера портов, не оставляй `ports: []`.
- PPR pipe `32x5.4 PN20`: сохрани outer diameter 32, wall thickness 5.4 и pressure class PN20.
- threaded valve female/female `1/2\"` (внутренняя/внутренняя резьба): размер не должен исчезнуть из обоих threaded ports.
- pipe support `M8 ... (25-29)`: M8 относится к крепежу и не является диаметром трубы; размер трубы — диапазон 25–29. Непредставимый факт оставь unresolved/ambiguity, но не записывай неверное `diameter_mm: 8`.

Минимальная canonical construction guidance: female-thread closure → `cap`; male-thread closure → `plug`; PPR + threaded mixed fitting → `adapter`. Не расширяй это до общего словаря эвристик: при неоднозначности исходный source важнее догадки.
