# Разметка заявки в `request_bundle`

Выполни эту инструкцию в новом чате, используя приложенные
`request-annotation-kit.json` и исходную заявку. Комплект является единственным
источником taxonomy, 41 класса, JSON Schemas и допустимых canonical values. Не
используй знания о контрактах вне комплекта и не изменяй и не встраивай его
содержимое в ответ.

## Результат

Для **каждого** исходного документа создай отдельный скачиваемый UTF-8
JSON-файл `request.<request_id>.json` с `kind: "request_bundle"`. Проверяй его
по `root_schema_id` комплекта:
`https://example.local/schemas/bundles/request-bundle.schema.json`, разрешая
ссылки только через embedded `schemas_by_id`.

Самостоятельно прочитай доступный чату Excel, DOCX, PDF, обычный текст или
вставленный в сообщение список. Не проси пользователя конвертировать,
подготавливать или разбивать источник. Большой документ можно обрабатывать
внутренними частями, но выдай один завершённый результат на документ. Нельзя
представлять частичный файл как готовый.

## Строки заявки

1. Выдели все товарные позиции и не смешивай несколько позиций в одну строку.
   Заголовки, подписи, реквизиты и итоги товарными позициями не являются. Не
   пропускай позиции без явного сообщения.
2. Сохрани исходный текст каждой позиции без смыслового переписывания в
   `raw_text`, а доступные строку, лист или страницу — в `source_position`.
   Создай стабильный `line_id` из позиции строки в документе.
3. `source.source_file_name` и
   `request_document.document.source_file` должны точно совпадать.
   `line_count` должен точно равняться количеству request lines.
4. Извлекай quantity только при её наличии в заявке; используй только
   canonical quantity units из kit.

## Требования и annotation

Для каждой позиции выбери один из 41 классов и примени соответствующую request
class schema из kit. Формируй **sparse constraints**: добавляй только явно
написанные требования и не превращай отсутствие требования в ограничение.
Всегда создавай `constraints.attributes` и `constraints.ports`, даже если они
пусты.

Извлекай лишь подтверждённые исходным документом сведения, ничего не
выдумывай. Неизвестные и неоднозначные требования сохраняй через annotation с
`unknown_fields`, `ambiguities` и `needs_review`, а не заменяй догадками. Для
каждого значения, полученного смысловой интерпретацией, добавь evidence. Все
ссылки на поля должны быть RFC 6901 JSON pointers. Ставь `validated` только
если выполнены требования выбранной class schema.

## Замена

Отражай разрешение или запрет замены в `substitution_statement` только если он
явно написан. При отсутствии явного утверждения используй ровно:

```json
{"policy":"unspecified","explicit":false,"raw_text":null}
```

Не предполагай допустимость аналога самостоятельно.

## Жёсткие запреты

- Не выполняй matching или подбор товаров, не обращайся к catalog data, не
  вычисляй similarity score и не создавай `product_id`, `offer_id` или
  `match_level`.
- Не исправляй, не проверяй, не угадывай и не нормализуй GTIN или артикулы.
- Не добавляй неподтверждённые характеристики.

Если документ нельзя надёжно прочитать либо нельзя построить полный валидный
bundle, остановись и сообщи конкретную причину вместо создания
правдоподобного неполного результата.

## Выдача и проверка

Перед выдачей программно проверь результат по `root_schema_id` и embedded
`schemas_by_id`. Не утверждай, что файл валиден, если программная проверка не
выполнена. Не печатай полный JSON в сообщении: приложи только скачиваемый файл.
После файла дай только краткую сводку: общее количество строк и количества
`validated`, `needs_review`, `invalid`.
