# ТЗ: ребалансировка остатков между подразделениями (MVP)

**Статус:** проект спецификации для согласования в PR; реализация не входит в этот PR.
**Продукт:** Auto Offer, отдельный модуль «Ребалансировка».
**Цель:** закрывать дефициты подразделений внутренними перемещениями из доступных запасов других подразделений, не создавая новый дефицит у донора и не формируя лишние перемещения.

## 1. Зафиксированные требования и границы

1. Источник нормативов — **уже готовые Min и Max** для пары «подразделение × артикул». Ребалансировщик их читает, **не рассчитывает и не редактирует**. Анализ истории продаж, сезонность и автоматическое определение Min/Max — будущий самостоятельный слой, не MVP.
2. Получателем может стать **только** подразделение, у которого доступный остаток артикула строго ниже его Min. Для подразделений с остатком от Min включительно не создаётся потребность, даже если до Max далеко.
3. По умолчанию донор отдаёт **только излишек сверх Max**, а получатель пополняется **не выше Max**. Эти начальные значения соответствуют двум независимым ползункам на 100%.
4. Ползунок донора определяет допустимый **минимальный остаток после отдачи** между собственными Min и Max; ползунок получателя — **верхний целевой остаток после получения** между его собственными Min и Max.
5. Прямые маршруты между подразделениями задаются матрицей наподобие турнирной сетки. По умолчанию разрешены все пары в обе стороны; маршрут можно отключить или оставить только одно направление, назначив, кто является донором для данной пары.
6. Есть независимые включаемые фильтры: цена за единицу, например **строго выше 1 000 ₽**, и **совокупная** стоимость перемещений одного артикула по всей сети, например **строго выше 10 000 ₽**. Ограничение на сумму не проверяется отдельно для каждого маршрута.
7. Выход — **предлагаемый план**, а не проведённые движения товара: откуда → куда → артикул → количество → стоимость, плюс итоги и причины исключений. В MVP не создаём документы 1С и не изменяем фактические остатки.
8. Модуль не затрагивает семантический подбор коммерческих предложений, STEP1–STEP3, каталог-разметку и существующие сессии Auto Offer.

## 2. Входные данные и ограничения качества

Один расчёт выполняется над фиксированным **снимком данных** с идентификатором/датой. Минимальные поля:

| Сущность | Обязательные поля |
| --- | --- |
| Подразделение | стабильный ID, человекочитаемое название, признак активности |
| Артикул | стабильный SKU/ID, название, единица учёта, шаг допустимого количества |
| Срез SKU × подразделение | SKU ID, подразделение ID, остаток на руках, резерв, готовые Min и Max |
| Цена артикула | учётная стоимость единицы в ₽, одна согласованная база оценки для всех перемещений данного SKU |

Доступный остаток S = фактический остаток − резерв. В MVP ожидаемые закупочные поступления и ранее подготовленные, но не отражённые перемещения не входят в S: это явно показывается в параметрах расчёта, чтобы пользователь понимал ограничения снимка.

Валидация перед расчётом: ID уникальны; для каждой пары SKU × подразделение не более одной записи; остатки и резервы неотрицательны; резерв не может превышать фактический остаток; 0 ≤ Min ≤ Max; шаг количества положителен; единица учёта SKU согласована между подразделениями; цена (если используется хотя бы один денежный фильтр) известна и неотрицательна. Невалидные/неполные строки **не выдумываются и не обнуляются молча**: они пропускаются с точной причиной и ссылкой на входную строку. Отсутствие нормативов для подразделения означает, что оно не может быть ни донором, ни получателем этого SKU.

Вход можно реализовать отдельным импортом структурированного снимка с явным отображением колонок; интеграцию чтения из 1С проектировать через заменяемый адаптер. Выбор конкретного транспорта (Excel/CSV, read-only 1С) — задача будущего implementation PR, не повод менять определения расчёта. В любом случае требуется возможность воспроизвести расчёт по сохранённому снимку.

## 3. Настройка маршрутов: матрица

- Визуально: квадратная матрица с одинаковым списком подразделений по обеим осям; диагональ недоступна, так как перемещение в себя запрещено.
- Одна неупорядоченная пара A/B имеет одно правило: **A ↔ B**, **A → B**, **B → A**, **запрещено**. Указание донора для однонаправленного правила означает **только сторону отправления**; в обратную сторону этот маршрут закрыт.
- По умолчанию все пары — **A ↔ B**. Предусмотреть переключатель «Все разрешены / Выборочные», переключение и сохранение явных исключений. В выборочном режиме пользователь включает/отключает пару галочкой и при необходимости выбирает направление; матрица зеркально показывает согласованное состояние той же пары. Раздельно включить A → B и B → A вместо третьего скрытого состояния запрещено.
- Запрещённый/однонаправленный маршрут **не открывается** автоматически из-за недостатка товара. Перемещения возможны только по прямой разрешённой дуге; транзит через третье подразделение не выполняется в MVP.
- При добавлении нового подразделения для новых пар действует общий default «разрешено в обе стороны», если пользователь не выбрал иной глобальный режим. Настроенные исключения и выбранный донор по существующим парам сохраняются.
- Масштабируемость: поиск и фильтрация строк/столбцов по названиям, закреплённые заголовки при прокрутке и счётчик активных направлений; матрица не должна требовать одновременного отображения всех N² интерактивных элементов на больших сетях.
- Настройки маршрутов сохраняются отдельно от входного снимка; запуск отчёта фиксирует их копию.

## 4. Два независимых ползунка Min–Max

Диапазон обоих ползунков **0…100%**, шаг UI по умолчанию 5%, начальное значение **100%**.

Для донора d:

    donor_floor(d,sku) = Min(d,sku) + (Max(d,sku) - Min(d,sku)) × donor_pct / 100

Для получателя r:

    receiver_target(r,sku) = Min(r,sku) + (Max(r,sku) - Min(r,sku)) × receiver_pct / 100

| Ползунок | 0% | 50% | 100% (default) |
| --- | --- | --- | --- |
| Донор: ниже какого остатка не отдаём | Min | середина Min/Max | Max |
| Получатель: выше какого остатка не поднимаем | Min | середина Min/Max | Max |

Оба расчёта используют **собственные** нормативы каждого подразделения. Ползунок **не задаёт процент от Max** и не заменяет сам Min/Max. Если Min = Max, оба порога равны этому значению.

Для неделимых штук/другого шага количества капы округляются **в безопасную сторону**: нижний порог донора вверх к ближайшему допустимому количеству, верхний предел получателя вниз. Количества перемещений кратны шагу данного SKU. При невозможности соблюсти кратность потребность остаётся частично незакрытой; запрещено округлять с нарушением нижней или верхней границы.

Считаем после каждого назначенного перемещения:
- donor_available = max(0, S_d − donor_floor_d) с учётом ещё не использованного остатка;
- receiver_need = max(0, receiver_target_r − S_r) **только** если S_r на исходном снимке был **строго ниже Min_r**;
- transfer_qty ≤ min(donor_available, receiver_need), с учётом шага количества, маршрута и всех уже распределённых движений.

**Жёсткие инварианты:** после предложенных перемещений каждый донор имеет остаток ≥ его donor_floor; каждый получатель — остаток ≤ его receiver_target, а значит **никогда выше собственного Max**. Один и тот же доступный остаток не расходуется дважды. Подразделение, начинавшее ниже Min, не используется как донор для этого SKU. При нулевом запросе или отсутствии допустимого прямого маршрута ничего не создаём.

## 5. Приоритеты и алгоритм распределения

Не достаточно отсортировать пары и раздать остатки жадно: это может оставить дефицит при наличии допустимого решения. Для каждого SKU строим ориентированный граф из разрешённых маршрутов; на каждом этапе максимизируем фактически закрываемую потребность при ограничениях на источник и получателя (задача распределения потока). Результат детерминирован для одинаковых данных и настроек: повторная загрузка и перестановка строк входа не меняют план.

Для MVP задаём лексикографический порядок целей:
1. **Дефицит до Min** у получателей закрываем раньше пополнения от Min до целевого уровня.
2. При одной и той же цели **сначала используем донора только сверх Max**.
3. Если осталось непокрытое и ползунок донора разрешает, можно использовать остаток **от Max вниз до donor_floor**, но ни одной единицы ниже.
4. После закрытия доступного дефицита до Min пополняем получателей дальше к receiver_target (не выше Max), снова сначала из surplus > Max, затем из разрешённого буфера ниже Max.
5. Если одинаково допустимы несколько решений, отдаём предпочтение меньшему числу строк перемещений (чтобы не дробить поставку), затем стабильному порядку ID. Это вторичный критерий: он **не должен ухудшать** первичную цель покрытия.
6. План без циклов самоперемещений; передача через промежуточного получателя и повторное использование полученного товара запрещены.

Содержательно четыре прохода: (A) сверх-Max → закрыть до Min; (B) разрешённый запас ниже Max → закрыть до Min; (C) сверх-Max → довести до target; (D) разрешённый запас ниже Max → довести до target. На каждом проходе учитываются остаточные ограничения после предыдущих. Такая последовательность сохраняет приоритет дефицитов и предпочитает безопасных доноров при равной цели; при невозможности полного закрытия показывается остаточная нехватка.

## 6. Фильтры экономической целесообразности

В блоке «Условия» отдельно включаются/выключаются:
- **Цена единицы:** price(sku) > threshold_price; пример 1 000 ₽. Проверять **до** распределения.
- **Сумма перемещений артикула:** sum(transfer_qty × price(sku)) > threshold_total; пример 10 000 ₽. Проверять **после предварительного распределения**, суммируя все прямые маршруты одного SKU по всем подразделениям за один запуск.

Сравнение в примерах строгое («выше»): при равенстве порогу условие **не выполнено**. Чтобы снять неоднозначность, UI прямо пишет оператор «строго больше», а не только «минимальная сумма». Если оба фильтра включены, действуют оба условия (AND). Если денежные фильтры выключены, отсутствие цены само по себе не блокирует количественное перемещение, но сумма в отчёте показывается как «нет цены», без вымышленного нуля.

Если общая сумма предварительных перемещений SKU не проходит порог, **исключаем все строки этого SKU**, а не отдельные маршруты. Сумму по SKU при исключении показываем в диагностике. Затем итоговые остатки и покрытие пересчитываются только по оставшимся строкам; недопустимые SKU не создают фиктивных движений или свободных остатков другого SKU. По умолчанию оба денежных фильтра **выключены**; 1 000 и 10 000 ₽ — примеры настраиваемых значений, не навязанные бизнес-пороги.

Отдельно от MVP: оптимизация логистических тарифов/расстояний, минимальная партия рейса и цена за направление. Экономический фильтр **не равен** доказанной логистической выгоде, и интерфейс не должен утверждать обратное.

## 7. UX MVP

Три рабочих раздела/вкладки без длинной вертикальной формы:

1. **Маршруты:** матрица, общий режим доступа, парные галочки, выбор донора/направления, сохранение изменений.
2. **Условия:** два независимых ползунка с подписями Min / 50% / Max и отображением вычисленного порога на примере SKU; включаемые денежные фильтры с указанием строгого сравнения; явная кнопка «Рассчитать».
3. **Результаты:** сводка (количество SKU, маршрутов и перемещений, сумма, закрытая потребность до Min, незакрытая потребность, исключения), таблица «артикул / откуда / куда / количество / цена / сумма / остатки до и после», группировка по артикулу либо маршруту, поиск и причины исключения.

Для каждой строки результата доступны исходные Min/Max сторон и применённые доли ползунков. Показываем суммарное покрытие и остатки **после всего плана**, а не изолированно по каждой строке. Нужны читаемые сообщения: «нет маршрута», «донор достиг порога», «получатель достиг цели», «ниже Min не было», «не проходит цена/сумма», «не хватает исходных данных».

Раздел результатов содержит экспорт **Excel (XLSX)** с листом перемещений, сводкой, исключениями и параметрами расчёта. Это рекомендация к исполнению, не документ движения 1С. Результат сохраняет связь со снимком входов, настройками маршрутов и фильтров, версией алгоритма и временем расчёта.

## 8. Технические границы и ответственность

- Разделить **чистый вычислительный домен** (валидация → потребность/излишки → граф → распределение → фильтры → итоги) и UI; функции домена не читают браузерный storage и не меняют входы.
- Отдельный слой импорта/адаптеров данных; не смешивать таблицы маршрутов и остатки с существующими catalog_bundle, request_bundle или semantic matching.
- Модели конфигурации маршрутов, ползунков, фильтров и результата — версионируемые. Перенос в IndexedDB делается отдельной миграцией с сохранением существующих каталогов и сессий. Никакой перезаписи бизнес-данных Auto Offer.
- Использовать стабильные ID вместо имён подразделений. Изменение отображаемого названия не должно менять правило маршрута. Изменение списка активных подразделений должно обнаруживать устаревшие направления.
- Не выполнять скрытые перемещения в 1С, не списывать товар, не менять Min/Max, не отправлять данные внешнему ИИ.
- Ограничить точку расширения: будущая интеграция с read-only 1С и отдельный модуль расчёта Min/Max подключаются через входной снимок, без изменения формул и правил этого MVP.

## 9. Приёмочные сценарии (must pass)

**AC-01 — дефолт:** донор Min=20, Max=60, S=80; получатель Min=20, Max=60, S=10. При 100%/100%, разрешённом маршруте — переместить **20**, остатки 60 и 30. Нельзя отдать 50, потому что донор не должен опуститься ниже Max.

**AC-02 — донор 50%:** при тех же входах донор может отдать **40**, новый остаток 40 (середина Min/Max), у получателя 50; верхний предел получателя Max=60 не нарушен.

**AC-03 — получатель 0%:** при дефолтном доноре, но target=Min=20, отдаём только **10**, остаток получателя 20. При исходном остатке получателя **20** не предлагаем ничего даже если target=Max.

**AC-04 — ограничение Max:** донор S=200, получатель S=10, получатель Min=20, Max=60: при target=100% предлагаем не более **50**, получатель после =60, независимо от избытка донора.

**AC-05 — однонаправленный маршрут:** A → B работает, B → A и заблокированная пара не работают независимо от сумм и остатков. Все пары по умолчанию разрешены в обе стороны. Диагональные перемещения запрещены.

**AC-06 — сеть, а не жадный порядок:** доноры D1 и D2 могут дать по 10, получатели R1 и R2 требуют по 10. D1 имеет дуги к обоим, D2 — только к R1. Должны получиться D1→R2 =10 и D2→R1=10 (покрытие 20), даже если сортировка «по ID» начала бы с D1→R1.

**AC-07 — цена и общий порог:** SKU стоит 1 200 ₽, рекомендации по двум направлениям 6 и 5 шт.; суммарно 13 200 ₽ — обе строки остаются при фильтрах price>1000 и SKU_sum>10000. Если осталось только 6 шт. (=7 200 ₽), исключаются **все** строки этого SKU. При равенстве порогу также исключаем.

**AC-08 — ограниченные доноры:** ни один донор не опускается ниже его собственного floor, независимо от числа получателей; не переиспользовать один остаток по нескольким парам.

**AC-09 — смешанные Min/Max:** при ползунке 50% для Min=5/Max=15 порог=10, для Min=40/Max=100 порог=70; не применять общесетевой абсолютный порог.

**AC-10 — частичный дефицит:** при нехватке предложения итоговый отчёт отражает реально закрытое количество и остаток потребности без искусственного перемещения.

**AC-11 — вход и детерминизм:** пропущенные/некорректные Min/Max, повторяющиеся SKU × подразделение, резерв больше остатка и невалидная цена при активном фильтре дают явные причины исключения. Один и тот же снимок с теми же настройками и перестановкой строк даёт тот же план.

**AC-12 — безопасность данных:** обновление страницы и повторный вход восстанавливают маршруты, условия и сохранённые результаты; текущие каталоги, заявки и selection state Auto Offer неизменны. Экспорт XLSX повторяет фактические строки и итоги отображённого плана.

## 10. Не входит в MVP

- Автоматическое вычисление/оптимизация Min/Max из истории продаж.
- Автозакупка и автозаказ поставщику после ребалансировки.
- Проведение и подтверждение внутренних перемещений в 1С; учёт их фактического исполнения.
- Расстояния, стоимость рейсов, оптимизация склада-посредника, многоступенчатые цепочки.
- Реальная синхронизация онлайн-остатков и резервирование запасов между пользователями.
- Автоматическая замена коммерческих предложений и любые изменения в STEP1–STEP3.
